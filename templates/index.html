STEP 6

Cryptographic Architecture & Theory

Signing Flow (Alice)

How Digital Signing Works

  1. 1
    Exact Bytes: Alice's plaintext message is encoded to exact UTF-8 bytes.
  2. 2
    SHA-256 Hash: Fixed-size 256-bit cryptographic digest computed from the bytes.
  3. 3
    RSA-PSS Padding: Salt and Mask Generation Function (MGF1) are applied for provable security.
  4. 4
    Private Key Operation: The padded hash is encrypted using Alice's Private Key $(S = m^d \pmod n)$.
  5. 5
    Signature Output: 256-byte binary signature encoded to Base64 for transmission.
Verification Flow (Bob)

How Verification Works

  1. 1
    Receive Payload: Bob receives plaintext message $M$, signature $S$, and Alice's Public Key $(e, n)$.
  2. 2
    Local Hash Calculation: Bob calculates $H_1 = \text{SHA-256}(M)$ directly on received text.
  3. 3
    Public Key Operation: Bob decrypts signature using Alice's Public Key $(H_2 = S^e \pmod n)$.
  4. 4
    PSS Unpadding & Compare: Bob verifies $H_1$ equals recovered $H_2$.
  5. 5
    Verdict: If $H_1 == H_2 \rightarrow$ VALID; If $H_1 \neq H_2 \rightarrow$ INVALID.

⚠️ Crucial Concept: Digital Signing vs Public Key Encryption

Dimension Digital Signature (What we do here) Public Key Encryption (Confidentiality)
Primary Goal Authenticity, Integrity & Non-Repudiation Confidentiality / Secrecy
Key Used to Create Sender's (Alice's) Private Key Recipient's (Bob's) Public Key
Key Used to Verify / Decrypt Sender's (Alice's) Public Key (Anyone can verify!) Recipient's (Bob's) Private Key (Only Bob can read)
Is Message Secret? NO — Plaintext is openly readable by anyone. YES — Plaintext is ciphertext, unreadable in transit.
Padding Scheme RSA-PSS (Probabilistic Signature Scheme) RSA-OAEP (Optimal Asymmetric Encryption Padding)

👤 1. Authentication

Successful verification proves that the signature was generated by the entity possessing Alice's unique private key. Since the private key never leaves Alice's custody, Bob is mathematically certain the message originated from Alice.

🛡️ 2. Integrity

Cryptographic hash functions (SHA-256) possess the avalanche effect and pre-image resistance. Changing even one bit of the plaintext message produces an entirely different hash, causing signature verification to fail immediately.

📜 3. Non-Repudiation

Alice cannot claim "I didn't send this" because only her private key could produce that valid signature. However, non-repudiation in real-world PKI also relies on trustworthy digital certificates (X.509) and secure key storage (hardware security modules).

Laboratory Demonstration Walkthrough (Checklist for Students)

Follow these exact steps in front of your examiner during the practical:

Phase 1: Key Generation

1. Explain to the examiner that RSA is an asymmetric cryptosystem requiring a public key $(e, n)$ and a private key $(d, n)$.

2. Click "Generate RSA Keys". Point out Alice's and Bob's 2048-bit public keys and SHA-256 fingerprints.

3. Key Viva point: Emphasize that the private keys are safely kept in backend memory and are never sent over HTTP.

Phase 2: Alice Signs the Message

1. Select the "Bank Wire" preset ("Transfer $5,000 from Alice...").

2. Click "Sign Message with Alice's Private Key".

3. Show the examiner the generated SHA-256 hash (64 hex characters) and the resulting RSA-PSS signature (256 bytes Base64 encoded).

4. Explain that Alice signs the hash, not the entire message, for computational efficiency and fixed size.

Phase 3: Network Transmission to Bob

1. Click "Send Message, Signature & Public Key to Bob".

2. Explain that the channel is unencrypted: Bob can read the message in plaintext. Digital signatures provide authenticity and integrity, not confidentiality.

Phase 4: Bob Verifies the Authentic Signature

1. On Bob's panel, click "Verify Signature (RSA-PSS)".

2. Show the green "VALID" banner. Point out that Bob used Alice's public key to verify that Alice signed it and that zero characters were modified.

Phase 5: Tampering Demonstration (MitM Attack)

1. Scroll to the Tampering Studio. Click "Change $5,000 to $9,000".

2. Point to the Avalanche Effect Visualizer: show how changing just one character completely scrambled the SHA-256 hash.

3. In Bob's panel, click "Verify Signature".

4. Show the red "INVALID" banner! Explain that Bob detected message alteration because the recalculated hash does not match the decrypted signature.

5. Click "Corrupt Signature" and verify again to prove that tampered signatures also fail.

Answer: RSA-PSS (Probabilistic Signature Scheme, specified in PKCS#1 v2.1) incorporates a randomized salt and a Mask Generation Function (MGF1). Unlike deterministic schemes like PKCS#1 v1.5, RSA-PSS produces a different signature every time even for the exact same message, which prevents chosen-ciphertext attacks and mathematical forging.
